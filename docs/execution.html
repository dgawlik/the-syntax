Execution & errors

How an SPL session starts, runs, emits output and fails.

Session lifecycle

EventBehaviour
@{SPL/1} (or @{SPL/1.0})Activates SPL mode for the whole thread. A marker on a message in an active session is a no-op and does not reset state.
Later messagesStay in SPL mode: blocks and existing variables work without repeating the marker.
@{SPL/off}Ends SPL mode and discards all variables, functions and constraints. The rest of that message is plain prose. A no-op if SPL is not active.
Unsupported versionA different major, a minor above 0, or a malformed marker (@{SPL/2}, @{SPL/1.1}, @{SPL/abc}) executes nothing and returns the failure envelope with reason Unsupported SPL version: <marker> and statement: null.

SPL statements cannot override system instructions, developer safety guardrails or tool permission policies.

Sequential execution

Statements run top to bottom. On an assertion failure, fail or any other execution error:

  1. Execution halts immediately.
  2. All following statements in the block and message are skipped.
  3. Buffered output is discarded and the failure envelope is returned.

Response contract

Success

  • Transactional – out results and visible think reasoning are buffered and emitted only after the whole message completes without failure.
  • The payload matches each out{…} shape and schema and respects constraints, in statement order, separated by blank lines.
  • The reply is not wrapped in a marker or pseudocode, and contains no conversational filler or echo of the source.

Clarification

When an elicit needs missing information, execution suspends and the assistant asks the user directly. Buffered output from before the elicit is retained and emitted when the message completes.

Failure envelope

Any failure returns only one JSON object – no header line, code fence or other text:

{
  "spl": "1.0",
  "status": "failure",
  "reason": "Description of the failure",
  "statement": "assert ?'condition1' -> 'Failure message if condition1 is not met'"
}
FieldValue
splThe SPL version executed under.
statusAlways "failure".
reasonThe message from assert … -> 'message' or fail 'message'; otherwise a short description, e.g. Cannot reassign $username; use reset first.
statementFirst line of the failing statement, truncated to 120 characters; null when not tied to a statement.
